# Evaluation harness

Answers one question: after changing a prompt, model, threshold or embedding, did Rekindle get better or worse? Each run executes Rekindle's real reconciler, retrieval and evaluator against a throwaway Postgres (Testcontainers) and scores the result against **labels written by a person**. The tooling never decides what is correct.

## Layout

```
evals/
  configs/        run configurations (providers, K, threshold, prices) and thresholds.json
  runner/         the TypeScript runner behind `pnpm eval`
  results/        one JSON per run: aggregate numbers only, committed
  REPORT.md       generated by `pnpm eval:report`
  dataset/        the committed synthetic dataset (no personal data)
  private/        git-ignored: your real notes, article texts, labels and caches
```

A dataset is a directory:

```
<dataset>/vault/Projects/<Project>/**.md   the projects, as in Obsidian
<dataset>/articles/<id>.json               { id, title, url?, source, text }
<dataset>/labels.yaml                      ground truth, filled in by the owner
<dataset>/cache/                           embeddings, summaries and recorded LLM answers
```

## Workflow

1. `pnpm eval:snapshot --vault <path> --out evals/private` copies the markdown of your projects (read-only on the vault).
2. List article URLs in `<dataset>/sources.yaml` (`- {id: x, url: https://…}`) and run `pnpm eval:fetch <dataset>`. Articles are fetched with Rekindle's own SSRF-safe fetcher and extracted with Readability (YouTube links use transcripts).
3. `pnpm eval:label <dataset>` writes `labels.yaml` with every verdict empty. **Fill it in**: for each article and project choose `actionable`, `tentative` or `irrelevant`, and, if you like, for `actionable` the `target_note` where you would use it (kept in the labels, not scored). Set `labeled_by`. `pnpm eval:label <dataset> --check --strict` validates it.
4. `pnpm eval run <dataset> --config evals/configs/<config>.json [--record]` runs a config. `--record` also stores each LLM answer so the run can be replayed.
5. `pnpm eval:review <dataset>` opens a local page (127.0.0.1 only) with every article, the summary the models saw, each model's verdict, confidence, reasoning and suggested action next to your label, and live metrics. Pressing a verdict button saves it to `labels.yaml` (a timestamped backup is made when the page starts), and the metrics update at once. It reads the per-config detail files in `<dataset>/runs/`, which each run writes; `pnpm eval run … --replay` regenerates them from the cache for free.
6. `pnpm eval:report` regenerates `REPORT.md`; `pnpm eval:check --dataset <name>` fails when a metric falls below `configs/thresholds.json`.

**Rate limits (free-tier Gemini).** In an eval, an HTTP 429 never falls back to another model, because that would silently turn a Gemini baseline into Qwen answers. The runner waits for the delay the provider suggests (or backs off exponentially, per the config's `rateLimit`), retries the same provider, and records a failed call if the limit does not lift. The report shows rate-limit hits and time waited. If the daily quota is spent the run stops, the cache keeps everything answered so far, and `--record` resumes later where it left off (failed calls are asked again).

`--replay` runs with no network and no models, using only the dataset's cache; it is deterministic. Recorded answers are keyed by the exact prompts, so any prompt change means re-recording: Phase 5's prompt-injection defenses changed every prompt, so the private top-3 configs were re-recorded at `ce14538` (the Phase 3 recordings replay only at `2c07568` or earlier), and the committed fixture `tests/fixtures/eval-mini` was re-recorded with local Ollama. Summaries are cached by article text and summary provider, not by prompt. A run stops before its estimated LLM spend exceeds `--max-usd` (default `EVAL_MAX_USD`, 0.50).

## What is measured

| Metric | Meaning |
|---|---|
| Precision@K / Recall@K | Are the projects the owner marked relevant among the top K retrieved? |
| False retrieval | Share of articles with no relevant project that still retrieved a project |
| Triage F1 | Per class and macro, from the confusion matrix (a project that was not retrieved counts as `irrelevant`) |
| Reliability | Malformed model outputs, fallbacks to another provider, failed calls |
| Latency, tokens, USD | p50/p95 per call; total tokens, the part of the input served from the provider's cache and the part of the output spent thinking, and the mean per triage call (runs from 2026-10-19 on); cost only where a price is configured, otherwise "not measured". Prices can set a cached-input rate and off-peak hours (`src/ai/pricing.ts`); recordings without call times are priced at peak, an upper bound |
| Telemetry | The run's own `llm_telemetry` and `pipeline_events`, summarized by the same code as `pnpm telemetry:report` (results from before Phase 4 do not have it). Run details carry each article's trace ID. |

Suggestion quality (relevance, usefulness, actionability) needs the owner's ratings and is **not measured** yet.

Target-note accuracy (did the suggestion name the note the owner would have picked) is **not measured**. It was scored until 2026-10-19 and dropped: the notes in the labeled projects were not good enough to judge which note a suggestion belongs in, so the number said little. Results recorded before then still carry it; the report no longer shows it. That a suggestion can only target an existing note of its project is enforced in code and tested (`tests/failure_target_path.test.ts`).

## Privacy

Everything under `evals/private/` is ignored by git. Result files contain numbers and config names only, never note or article text (a test checks this). The committed dataset must stay synthetic.

## Fixture

`tests/fixtures/eval-mini/` is a three-article dataset whose labels are marked `labeled_by: test-fixture`. It exists to test the machinery offline; the report flags it as such.
