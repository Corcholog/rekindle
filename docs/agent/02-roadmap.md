# Roadmap

Work one phase per session, only when the owner names it. For every phase: plan first, wait for approval, implement in small commits, verify, then tick the checkbox and add an entry to `docs/JOURNEY.md`.

Order rationale: less code first (cleanup) makes every later step cheaper; security and integrity fixes come before anything is published; the eval harness comes before any retrieval or prompt tuning so that every change has a before/after number.

## Phase 1 — Cleanup: dead code and legacy

**Goal:** remove what no longer makes sense, with no behavior change.

**Steps**
1. Start from the audit's "Dead code and legacy inventory". Propose a removal list grouped by area; the owner approves or edits it.
2. Create a git tag `pre-cleanup`. Run typecheck, lint, and all tests (including integration with throwaway containers) to record the baseline.
3. Remove in small commits, one group at a time: unused code, unreferenced routes, unused dependencies, stale scripts and tests, outdated docs.
4. DB objects: never edit applied migrations. Add new migrations that drop abandoned tables, columns, enums, or indexes; call out any data loss explicitly and wait for approval.
5. For "Legacy but live" items, document them or open a note in `docs/JOURNEY.md`; do not rewrite them in this phase.

**Acceptance criteria**
- Every removal is on the approved list and has evidence in the report.
- Typecheck, lint, and tests pass after every commit, with the same or better coverage as the baseline.
- No endpoint, UI element, or script used by the web UI, the extension, or `package.json` was removed.
- Docs and the architecture document updated to match; the drift table from the audit is closed.
- `docs/JOURNEY.md` lists what was removed and why.

## Phase 2 — Fix Critical and High findings

**Goal:** close the findings that could corrupt the vault, leak data, or be exploited from a web page.

**Rules:** one finding per commit or small group; each fix has a regression test that fails before the fix and passes after; path and URL boundaries are enforced in code, independent of the LLM; sanitize LLM output before it is written to the vault or rendered.

**Acceptance criteria**
- Every Critical and High finding is fixed, or explicitly accepted by the owner with a written reason in `docs/JOURNEY.md`.
- Invariants I1–I7 each have a test or a documented verification.

## Phase 3 — Evaluation harness

**Goal:** answer "how do you know the system got better after changing the prompt, model, threshold, or embedding?"

**Layout**
```
evals/
  dataset/            labeled cases (JSONL), owner-labeled
  configs/            model/threshold configurations to compare
  runner/             TypeScript runner, `pnpm eval`
  results/            timestamped outputs (git SHA + config hash in each)
  REPORT.md           latest report, generated by the runner
```

**Dataset**
- Start with 30–50 carefully labeled cases built from `demo_vault` or sanitized real material, then grow from real failures.
- **The owner labels ground truth.** The agent builds the schema, a labeling helper/template, and the tooling; it never decides which answer is correct. A small reviewed set beats thousands of synthetic cases that merely agree with the model.
- Each case: content (or a fixture reference), the project/vault state, expected relevant projects, expected target note, expected verdict, and notes.

**Metrics**

| Component | Measure |
|---|---|
| Project retrieval | Precision@K and Recall@K: are the relevant projects retrieved? |
| Note targeting | Percentage of suggestions that name the correct target note |
| Triage classification | Precision, recall, and F1 for actionable / tentative / irrelevant |
| Suggestions | Human-rated relevance, usefulness, and actionability (1–5, owner-rated) |
| Citation grounding | Do cited sources actually support the generated claims? |
| Staleness | Correct handling of keep_or_refine / already_addressed / obsolete |

**Comparisons:** run at least two configurations on the same cases (local Qwen vs Gemini) and record quality, latency, and failure rate (timeouts, malformed structured output). Also support threshold sweeps for retrieval.

**Acceptance criteria**
- One command (`pnpm eval`) runs end to end and writes a report the owner can commit.
- Runs are reproducible: seeds and settings recorded; deterministic mode for CI using recorded fixtures.
- The report states dataset size, who labeled it, known weaknesses, and per-config results.
- A regression check can fail when a change drops a chosen metric below a threshold.

## Phase 4 — AI observability

**Goal:** make model behavior measurable without collecting more personal content than necessary.

**Track**
- Correlation ID from ingestion through retrieval to the resulting suggestion.
- Latency per stage: embedding, retrieval, LLM generation, total job duration.
- Reliability: retries, malformed structured outputs, provider fallback, queue failures.
- Cost: token usage and estimated cloud cost where usage data is available.
- Retrieval: selected projects and notes, distances, number of candidates.
- Quality: link evaluation results from Phase 3 to the same trace fields.

**Rules:** by default, never log note text or full prompts; log IDs, lengths, hashes, and counts. Extend `llm_telemetry` with new migrations. Structured logs plus a small report command or dashboard are enough; no commercial platform required.

**Acceptance criteria**
- Any suggestion can be traced back to its source content and the retrieval step that produced it.
- A report command shows latency, fallback rate, failure rate, and cost over a period.
- A test proves that prompts and note text are not written to logs.

## Phase 5 — CI, integration and failure-scenario tests, threat model

**Goal:** turn architectural promises into tested guarantees.

**Deliverables**
- CI workflow (GitHub Actions): typecheck, lint, unit tests, and integration tests with a pgvector Postgres service container, on every push and pull request.
- A fake LLM/embedding provider and recorded fixtures so AI behavior is tested deterministically without live API calls.
- Tests for the eight failure scenarios listed in the audit (invalid or timed-out LLM output; Gemini and Ollama both failing; duplicate or interrupted jobs; note changed during reconciliation; accepted suggestion with failed disk write; prompt injection in retrieved content; SSRF and redirects; LLM-supplied path outside the project).
- `docs/THREAT_MODEL.md`: assets, untrusted inputs, mitigations, and residual risks, matching the audit's threat model.

**Acceptance criteria**
- CI passes from a clean checkout and shows a badge in the README.
- Every failure scenario has a test; every threat-model mitigation points to the test that proves it.

## Phase 6 — Reproducibility, demo, and real-user workflow test

**Goal:** someone else can run Rekindle and judge it.

**Deliverables**
- `.env.example`, documented prerequisites, predictable migrations, a demo vault, and a one-command start (extend `docker-compose.yml` if needed). Verify by following the README from a clean clone.
- A recorded demo (script and shot list prepared by the agent; recording by the owner).
- `docs/USER_TEST.md`: a defined workflow for 3–5 testers and what to record: time to first useful suggestion, percentage of suggestions accepted, and the most common reasons for rejection. Testers use the demo vault or their own data; their content is not stored in the repo.

**Acceptance criteria**
- A new machine reaches a first suggestion following only the README.
- User-test results are recorded only from real sessions; otherwise the README says "not measured".

## Phase 6.5 — Bilingual Rekindle (Spanish / English)

**Goal:** an English-speaking reader can run the demo end to end in English, and the language the model is instructed in is chosen by measurement.

**Deliverables**
- Interface, generated text and vault callouts in Spanish or English (`LANGUAGE`, `OUTPUT_LANGUAGE`, `NOTES_LANGUAGE`), with a Settings card.
- Summaries in the notes' language; instruction language fixed by the evals.
- An English demo vault; a fresh clone starts in English.
- Three measured experiments on the labeled set: English output (E1), English summaries against Spanish notes (E2), English instructions (E3).

**Acceptance criteria**
- With everything Spanish, prompts are byte-identical to the measured ones (replay test).
- A clean clone with `LANGUAGE=en` and no cloud key reaches an English suggestion and an English callout.
- E1–E3 results are committed and the defaults follow them; unmeasured combinations are written "not measured".
